## Findings

**F1 — should-fix. Two bad states that alternate, with no `ok` between them, file a new item on EVERY cycle.**

The [INFERENCE] "bad→a different bad files again" (`decide`: `if *state == last { Nothing }` and otherwise `File`)
means the alert is only re-armed when the *state value* changes, not when the service recovers. The design and the
Plan define a crossing as "a service going bad", and they keep the dead scanner's rule: "only a measured `ok` clears
an alert". Under this code, a service that never recovers can file without limit.

The realistic case is in DESIGN §2 itself. A provider at its cap answers 429, which reads as:
- `rate_limited` when the 429 carries `retry-after`;
- `quota_exhausted` when it carries no retry window.

So the reading alternates as the headers vary. `degraded` ↔ `rate_limited` is the same pattern.

To measure it, I added a scratch test to a temporary copy of the T file. It used the T file's own `file_rig`/
`put_and_alert`, ran 10 alert cycles over alternating fresh rows, and was deleted afterwards (`git status --short`
clean):
```
cargo test -q --test zz_rv rv_flapping -- --nocapture
RV rate_limited<->quota_exhausted: 10 cycles -> nusy-kanban creates = 10
RV ok<->degraded: 10 cycles -> nusy-kanban creates = 5
RV degraded<->rate_limited: 10 cycles -> nusy-kanban creates = 10
```
Ten cycles produced ten signals for one outage that never cleared. On this board a signal is a Captain's open
question, so each of these lands in the Captain's queue.

*Fix:*
- Once `alert.<key>` holds a non-`ok` state, a different bad state files nothing.
- The code may rewrite the entry's `state`, or keep a `last_seen`, and print the change on stdout, but only a
  measured `ok` re-arms the key.
- Change `the_crossing_rule`'s bad→bad assertion to match, and add a T-style test where alternating
  `rate_limited`/`quota_exhausted` over 10 cycles files ONE.
- Update DESIGN §3 "Alert — what EXP-004 built" to match.

If the author wants the operator to see that the bad state changed, the right channel is a `comment` on the filed
item, which the design doesn't provide, or a stdout line. A new item is the wrong channel.

**F2 — nit. `ok` ↔ `degraded` flapping files one signal per return to `degraded` (5 in 10 cycles, measured above).**

This follows the agreed rule, since a measured `ok` re-arms. But `degraded` is a soft state: latency over a
threshold, or a subscription window at or above warn %. The subscription kind runs every hour, so a window hovering
at warn % can file up to about 12 signals a day per account.

*Fix:* nothing in code without a ruling. Record this as an open question on the board for the Captain (whether
`degraded` files, or whether there should be an `[alert] states = […]` filter), and say in DESIGN §3 that it is
open. This review files nothing.

**F4 — nit. `alert.<key>` entries are never removed, and the write is unconditional.**
- A service removed from the config leaves its entry in `ai_status` forever. That is harmless, and readers skip it.

  than the revision-conditional write that EXP-003 built for rows. DESIGN runs `alert` once, after each probe cycle
  on the probe host, so neither is a problem today.

*Fix:* a sentence in DESIGN §3, and optionally `update` with the read revision in `put_entry` for the bus backend.
