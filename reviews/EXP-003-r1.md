**C5. Change subject: the publish-on-change rule and the row's safety.** `NatsKv::put` returns early on a failed
JetStream publish or ack, so no announce happens without a stored row. The announce runs after the ack, and its result
is discarded (`let announced = … .is_ok()`), so a failed announce cannot fail the put or lose the row. I checked this
by reading `src/backend.rs` `put`. No test covers it (see F4). `exp003_change_subject` passed (`test result: ok. 1
passed`). It shows that an unchanged state with a different latency publishes nothing, a change publishes exactly one
message on `ai.status.changed.<key>` carrying the row, and the recovery is announced too. **Cost:** one extra KV `get`
per row written. At the design's cadence (around 8 API rows every 12 h, 7 subscription rows every 1 h) the cost is
negligible. The race is F2.

## Findings

**F1 (should-fix): a healthy subscription seat with `roles` becomes the pick, and line 1 is then a service id, not a model.**
The config accepts `roles` on `kind = "subscription"`. `select` admits a subscription service whenever its role
matches, and `slots()` gives the service id as the "model" (`Kind::Subscription => vec![self.id.clone()]`). T's own
fixture configures `copilot` with `roles = ["review"]`, then keeps it `quota_exhausted` in every test ("whether a
healthy subscription seat is a review candidate is not settled by the design"). So the reachable path is untested, and
`an_exhausted_subscription_is_refused` passes vacuously. I probed it with a throwaway test (fixture copied from
`tests/exp003_select.rs`, copilot set to `Ok`, `--prefer fastest`). I deleted the test file afterwards, and
`git status --short` was clean.
```
$ cargo test -q --test zz_rv_probe -- --nocapture
RV github copilot | ok 30s ago (ttl 3600s); role review; family openai; cost unset; latency 90 ms; context unset; ranked by fastest
RV deepseek deepseek-v4-flash | ok 30s ago (ttl 3600s); ...
```
`$(quotabus select --role review --exclude-family anthropic --prefer fastest)` would then yield `github copilot`.
`copilot` is not a model id, and the latency is the usage read's wall time, not a model's. That breaks §3's CLI
contract ("prints `provider model`"). The wiring note's provider map has no `github` arm, so nusy-product-team's step
would rc 2 and run no review, even though healthy metered reviewers exist.

The design pulls two ways here. §1 names the motivating failure as the Copilot subscription running out mid-review, and
it lists "the loop skills choosing a reviewer model" as users, so a Copilot seat IS a reviewer source. But §2 makes a
subscription row per ACCOUNT, with the service id in the model slot, so the selector has no model to print for it. The
same tension leaves the `subscription` cost rank (C9) dead in practice.

**Fix:** until the Captain rules, make subscription seats never candidates. Do this in `select`, by skipping
`Kind::Subscription`, or in config, by refusing `roles` on a subscription service with a message. Say so in the
DESIGN "Selector — what EXP-003 fixed" block, replacing "a service with no `roles` (a Claude subscription account) is
never a candidate", and add a test with copilot `Ok`, plus a control. Then raise a SIG: "should a subscription seat
gate the selection of a model it serves (e.g. a `serves = [...]` or `review_model`), and at what cost rank?" The
alternative is to emit a real model for a seat, which needs that ruling first.

**F2 (nit): the change subject's read-then-write is not atomic.** With two concurrent writers of one key it can miss
an announcement. `put` reads the previous state with `store.get` and then publishes the new row unconditionally. The
interleaving: A reads `ok`, B reads `ok`, B writes `quota_exhausted` (announced), then A writes `ok`. A saw `ok` before,
so A announces nothing. The bucket is now back at `ok`, but the last announcement a subscriber saw says
`quota_exhausted`, and it stays wrong until the next change. Two writers can also both announce one change (a
duplicate, which is harmless). The design has one central probe, so this needs an overlap: the launchd tick
(`probe` every 300 s) plus a manual `probe --force`, or two hosts configured as the probe host. I found this by
reading `src/backend.rs` `put` (the `read_raw` then `publish_with_headers` sequence). I did not reproduce it live.
**Fix:** either document the single-writer assumption next to the DESIGN change-subject row, or make the write
conditional. Carry the read entry's revision and publish with `Nats-Expected-Last-Subject-Sequence: <rev>` (0 when
absent). On a wrong-last-sequence error, re-read and retry, so the announce decision is made against the state that
was actually replaced. Subscribers must re-read the row anyway: the subject is a hint, not the truth.

**F3 (nit): the wiring note says "the healthiest candidate first"** (`docs/wiring/nusy-product-team.md:26`), but
every candidate is equally a fresh `ok`. The order is `--prefer`, which defaults to `cheapest` (cost class, then
latency, then context). **Fix:** say "the first candidate in `--prefer` order (default `cheapest`)".

**F4 (nit): "a failed announce never loses the row" is true by construction but untested,** and the announce's
`client.flush()` has no timeout, unlike the put, which runs under `BUS_TIMEOUT`. I checked by reading `src/backend.rs`
`put`; `tests/exp003_change_subject.rs` has only the one happy-path test. **Fix:** wrap the flush in
`tokio::time::timeout(BUS_TIMEOUT, …)`. A cheap control is optional: assert that `put` returns `Ok` and the row reads
back after the client's connection drops between the ack and the announce.
